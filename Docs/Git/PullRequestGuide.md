# Pull Request 작성과 리뷰

작업한 브랜치를 `main` 에 합치는 유일한 통로입니다. `main` 에는 직접 push하지 않습니다.

## 우리 팀의 운영 방식

| 항목 | 규칙 |
|---|---|
| 리뷰어 | **팀원 1명 이상**을 지정합니다 |
| 병합 | 승인이 나면 **작성자 본인이** `Merge pull request` 를 누릅니다 |
| 강사 | 사후에 확인합니다. 승인을 기다릴 필요는 없습니다 |
| 셀프 승인 | 금지. 본인 PR은 본인이 승인하지 않습니다 |
| 응답 시간 | 리뷰 요청을 받으면 **반나절 안에** 답합니다 |
| 병합 후 | 브랜치를 원격·로컬 모두 지웁니다 |

리뷰가 밀리면 다른 사람의 작업이 멈춥니다. 자세히 못 보겠으면 "이 부분만 봤다" 고 적고 승인해도 됩니다. **아무 반응 없이 두는 것이 가장 나쁩니다.**

---

## PR 만들기

1. 브랜치를 `Push origin` 합니다.
2. GitHub 저장소 화면에 뜨는 `Compare & pull request` 를 누릅니다.
3. base가 `main`, compare가 내 브랜치인지 확인합니다. <mark>방향이 반대면 전혀 다른 일이 벌어집니다.</mark>
4. 제목과 본문을 작성합니다.
5. 오른쪽에서 리뷰어를 지정합니다.
6. 채널에 링크를 올려 리뷰를 요청합니다.

## 제목

커밋 메시지와 같은 형식을 씁니다.

```
[Feat] 몬스터 부채꼴 시야 감지 구현
```

## 본문

`Templates/PullRequestTemplate.md` 를 복사해서 채웁니다. 저장소 루트의 `.github/PULL_REQUEST_TEMPLATE.md` 에 같은 내용을 넣어 두면 PR을 만들 때 자동으로 채워집니다.

담을 내용은 셋입니다.

- **무엇을 했는가**: 변경 항목을 목록으로
- **왜 했는가**: 필요하면 한두 줄
- **확인한 것**: 어떤 상황에서 직접 돌려 봤는지

UI나 눈에 보이는 변화가 있으면 **스크린샷이나 짧은 영상**을 붙입니다. 리뷰어가 프로젝트를 열어 보지 않아도 판단할 수 있습니다.

## 올리기 전 확인

- [ ] Unity에서 실제로 실행해 봤는가
- [ ] 콘솔에 에러가 없는가
- [ ] 관계없는 파일이 같이 들어가 있지 않은가 (특히 다른 사람의 씬)
- [ ] 씬 파일이 들어갔다면, 내가 그 씬의 소유자가 맞는가

## 리뷰하는 쪽

`Files changed` 탭에서 바뀐 부분을 봅니다. 모든 줄을 이해할 필요는 없습니다. 아래 정도만 봐도 충분합니다.

- 이 변경이 **내 작업에 영향을 주는가**
- 내가 만든 스크립트나 프리팹을 건드렸는가
- 씬 파일이 들어가 있는데, 그 씬 소유자가 아닌 사람이 올린 것은 아닌가
- 읽었을 때 **무슨 일을 하는 코드인지 알 수 있는가**

코멘트는 줄 옆의 `+` 를 눌러 그 줄에 답니다. 마지막에 `Review changes` 에서 `Approve`(승인) 또는 `Comment`(의견만) 를 고릅니다.

### 리뷰 태도

- 코드에 대해 말하고 사람에 대해 말하지 않습니다.
- 모르면 물어봅니다. "이 부분이 왜 필요한지 모르겠다" 는 좋은 리뷰입니다. 리뷰는 서로의 코드를 읽는 거의 유일한 기회입니다.
- 사소한 지적도 괜찮습니다. 다만 **동작에 문제가 되는 것**과 **취향 차이**는 구분해서 적습니다.

## 병합

승인이 나면 작성자가 `Merge pull request` 를 누릅니다. 이어서 `Delete branch` 로 원격 브랜치를 지우고, GitHub Desktop에서 `main` 으로 이동해 `Pull origin` 합니다.

병합 후 `main` 이 정상 동작하는지 한 번 실행해 봅니다. **`main` 이 깨진 채로 방치되면 팀 전체가 멈춥니다.** 문제가 있으면 즉시 채널에 알립니다.
