# 팀 그라운드룰

이 문서는 코드 규칙이 아니라 **사람이 지키는 약속**입니다. 9일 동안 5명이 같은 저장소에서 작업하면서 실제로 문제가 생기는 지점만 모았습니다.

규칙을 많이 만드는 것이 목적이 아닙니다. 아래 항목은 지키지 않으면 곧바로 다른 사람의 작업이 멈추는 것들입니다.

---

## 1. 시간과 소통

| 항목 | 약속 |
|---|---|
| 코어타임 | (시간 기입). 이 시간에는 전원이 연락 가능한 상태로 있습니다 |
| 소통 채널 | (채널명 기입) 하나로 고정합니다 |
| 응답 기준 | 코어타임 중에는 30분 이내에 확인하고 답합니다 |
| 데일리 체크인 | 작업 시작 시 오늘 할 일을 채널에 한 줄 공유합니다 |
| 데일리 체크아웃 | 작업 종료 시 작업일지를 쓰고 커밋한 뒤 마칩니다 |

연휴 기간이라 각자 일정이 다릅니다. **빠지는 날이 있으면 미리 알립니다.** 말없이 사라지는 것이 가장 큰 문제입니다. 하루 쉬는 것 자체는 문제가 되지 않지만, 그 사실을 아무도 모르면 그 사람이 맡은 기능을 기다리느라 다른 작업까지 멈춥니다.

## 2. 막혔을 때

<mark>30분 넘게 같은 자리에서 진전이 없으면 질문합니다.</mark>

혼자 오래 붙잡는 것은 성실함이 아니라 팀 전체의 시간을 쓰는 일입니다. 9일 중 반나절을 혼자 헤매면 그만큼 완성도가 깎입니다. 질문할 때는 다음 세 가지를 같이 적습니다.

- 무엇을 하려고 했는가
- 어떻게 시도했는가
- 무엇이 나왔는가 (에러 메시지는 그대로 복사)

### 강사를 부르는 기준

아래 상황은 혼자 처리하지 말고 바로 강사에게 알립니다. 잘못 건드리면 복구가 어려워지는 것들입니다.

- 충돌이 났는데 어느 쪽을 남겨야 할지 판단이 서지 않을 때
- 씬 파일이나 `.meta` 파일에 충돌이 났을 때
- `main` 브랜치의 프로젝트가 열리지 않거나 에러로 실행되지 않을 때
- 파일이나 폴더를 실수로 지웠을 때
- Git에서 무언가를 되돌리려는데 어떤 버튼을 눌러야 할지 모를 때

## 3. 작업 분담

- 기능별 담당자와 씬 소유자는 `ProjectSpec.md` 에 적습니다.
- <mark>남이 맡은 씬은 열어서 보기만 하고 저장하지 않습니다.</mark> 저장하는 순간 충돌 대상이 됩니다.
- 남의 담당 스크립트를 고쳐야 하면 먼저 담당자에게 말합니다.
- 담당이 바뀌면 `ProjectSpec.md` 를 고칩니다.

## 4. 작업 범위

<mark>기능을 임의로 추가하지 않습니다.</mark>

"이것도 있으면 좋겠는데" 는 9일짜리 프로젝트에서 가장 위험한 문장입니다. 추가하고 싶은 것이 생기면 채널에 올리고 팀이 합의한 뒤에 시작합니다. 합의된 변경은 `ProjectSpec.md` 에 반영합니다.

**완성되지 않은 게임보다, 작아도 끝까지 돌아가는 게임이 낫습니다.** 발표회에서 보여 줄 수 있는 것은 계획이 아니라 실제로 실행되는 빌드입니다.

## 5. 일정

| 날짜 | 내용 |
|---|---|
| 2026-09-19 ~ 09-25 | 기능 구현 |
| 2026-09-26 | <mark>기능 동결</mark>. 이날 이후로는 새 기능을 넣지 않고 버그 수정과 다듬기만 합니다 |
| 2026-09-27 | 발표 준비만 합니다. 전원이 발표자료를 만듭니다 |
| 2026-09-28 | 발표회 |

기능 동결일이 있는 이유는 **마지막에 넣은 기능이 가장 많은 버그를 만들기 때문**입니다. 발표 전날 들어간 코드는 검증할 시간이 없습니다.

## 6. 리뷰와 대화

- 코드에 대해 말하고 사람에 대해 말하지 않습니다. "이 부분이 이렇게 동작하면 문제가 생길 것 같다" 는 리뷰이고, "왜 이렇게 짰냐" 는 리뷰가 아닙니다.
- 지적을 받는 쪽도 코드에 대한 말로 받습니다. 모두 배우는 중이고, 리뷰는 서로의 코드를 읽는 유일한 기회입니다.
- 모르는 것을 모른다고 말하는 것이 팀에 도움이 됩니다. 아는 척하고 넘어간 부분은 나중에 반드시 문제가 됩니다.

## 7. 저작권

외부 에셋(모델, 텍스처, 음원, 폰트 등)을 받으면 **받은 그날 바로** `AssetCredits.md` 에 출처와 라이선스를 적습니다.

발표회에서 공개하는 결과물이므로 출처를 밝힐 수 없는 에셋은 쓸 수 없습니다. 나중에 한꺼번에 정리하려고 하면 어디서 받았는지 기억나지 않습니다.

## 8. 기록

- 채널에서 결정된 내용은 반드시 문서에 옮깁니다. 채팅은 흘러가고 문서는 남습니다.
- 작업일지는 매일 씁니다. 분량은 짧아도 됩니다. **안 쓴 날이 생기는 것이 문제입니다.**
- 기술문서는 기능이 동작하게 된 시점에 씁니다. 다 끝나고 몰아서 쓰면 왜 그렇게 했는지 기억나지 않습니다.
